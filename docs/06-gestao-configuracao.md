# Gestão de Configuração e Manutenção

Este capítulo descreve como os artefatos produzidos ao longo do projeto do Sistema Unespão são versionados e mantidos sob controle, e como uma alteração feita em qualquer ponto do sistema pode ser acompanhada até seu efeito nos demais artefatos relacionados. O que está descrito aqui é o que a equipe efetivamente faz no repositório do projeto, sem inventar um processo mais formal do que o que está em uso.

## Repositório e itens de configuração

O projeto é versionado em um repositório Git hospedado no GitHub, com a branch `main` funcionando como ponto de referência para a versão consolidada do trabalho. O README atual descreve o repositório de forma sucinta como "nosso repositório para servir de KB do nosso projeto", frase que já dá uma ideia de como o Git ali serve tanto ao código quanto aos artefatos de documentação da disciplina.

Os principais itens de configuração controlados no repositório são o código-fonte da API back-end, desenvolvida em .NET 8/ASP.NET Core, responsável pela lógica de negócio, pelos endpoints consumidos pelo front-end e pela integração com o gateway de pagamento e demais adaptadores externos; o código-fonte do front-end, um SPA que implementa as telas de totem e de aplicativo do cliente, no framework definido no capítulo de Arquitetura para o projeto; o código dos testes automatizados descritos no capítulo de Estratégia de Testes, versionado junto do código de produção que ele cobre; as migrations do banco de dados, geradas via Entity Framework Core, que descrevem de forma incremental a evolução do esquema do PostgreSQL usado pelo sistema; a documentação do projeto, incluindo os arquivos fonte em LaTeX (`.tex`) deste documento e arquivos de apoio em Markdown (`.md`), como o próprio README; os diagramas C4 (Contexto, Contêineres e, quando aplicável, Componentes) usados para descrever a arquitetura do sistema nos capítulos anteriores; e o arquivo de referências bibliográficas (`refs.bib`), que consolida as fontes citadas ao longo da documentação. Esses últimos itens de documentação (fontes LaTeX, `refs.bib` e imagens de apoio) devem ser efetivamente adicionados e commitados no repositório antes da entrega, mantendo-os sob o mesmo controle de versão do código.

Um ponto de atenção sobre configuração sensível: a API depende de dados como a connection string do PostgreSQL e as credenciais do gateway de pagamento, que por natureza não deveriam ser commitados em texto plano junto do código-fonte. Nas fontes disponíveis do repositório não há evidência de uma separação formal já em uso para isso — não há, por exemplo, um `appsettings.Development.json` versionado com placeholders e um `appsettings.json` de produção fora do controle de versão, nem um `.gitignore` que explicite esse tipo de arquivo, nem uso de variáveis de ambiente documentado. Registramos isso como uma lacuna observável do estado atual do projeto, e não como algo já resolvido: à medida que a API for de fato implementada, esses segredos precisam ficar fora do Git (via variáveis de ambiente, `appsettings.Development.json` ignorado por `.gitignore`, ou mecanismo equivalente), mantendo apenas arquivos de configuração com placeholders sob versionamento.

Tratamos as migrations como item de configuração porque, assim como o código, elas precisam estar sincronizadas com a versão da aplicação que as acompanha: uma API em determinada versão espera um esquema de banco em estado compatível, e um descompasso aí quebra a aplicação mesmo com o código correto. Todos esses itens convivem no mesmo repositório, o que ajuda a manter código e documentação evoluindo juntos. Quando uma decisão de arquitetura muda, por exemplo, o diagrama C4 correspondente e o texto do capítulo de Arquitetura costumam ser atualizados no mesmo conjunto de commits.

## Gestão de dependências e alterações

As dependências externas são gerenciadas separadamente em cada camada da aplicação, seguindo o gerenciador de pacotes padrão de cada ecossistema. No back-end, as dependências do .NET — bibliotecas do próprio ASP.NET Core, driver do PostgreSQL, pacote do Entity Framework Core, cliente do gateway de pagamento, entre outras — são declaradas no arquivo de projeto `.csproj` e resolvidas pelo NuGet, que também registra as versões exatas utilizadas. No front-end, as dependências do SPA são declaradas no `package.json` e gerenciadas pelo npm, com as versões efetivamente instaladas fixadas no arquivo de lock correspondente.

O histórico do repositório mostra ainda que a equipe já adota Pull Requests como mecanismo de integração de mudanças à `main`, em vez de commits diretos. Isso aparece de forma explícita no próprio log do Git, com merges de PR registrados como eventos distintos do desenvolvimento (algo detalhado na seção de Rastreabilidade a seguir). Esse fluxo dá à equipe um ponto de revisão antes que qualquer mudança chegue à versão principal do projeto.

Quando uma alteração afeta mais de um artefato — por exemplo, uma mudança na regra de negócio do estoque que exige ajuste na API, uma migration nova e um trecho do capítulo de Arquitetura que descreve o `EstoqueService` (o serviço responsável por isolar a lógica de estoque, conforme o princípio de responsabilidade única discutido no capítulo de Arquitetura) — a expectativa é que essas mudanças entrem no mesmo Pull Request, de modo que a revisão avalie o conjunto coerente em vez de partes soltas. Isso ainda não está formalizado como uma convenção escrita da equipe (não há, por exemplo, um guia de contribuição ou template de PR no repositório), mas é a prática que o histórico de commits sugere até aqui.

## Rastreabilidade

Um exemplo real e observável de rastreabilidade no projeto é o próprio histórico de integração via Pull Requests. O log do Git mostra, entre os commits mais recentes, os merges "Merge pull request #2 from 00davidsarago00/docs" e "Merge pull request #1 from 00davidsarago00/00davidsarago00-patch-1". Cada um desses merges corresponde a um Pull Request identificável (#1 e #2) que passou por revisão no GitHub antes de ser incorporado à `main`, ou seja, dá para partir do identificador do PR e chegar ao conjunto de commits e arquivos que ele trouxe para o projeto.

**Figura 1** — Linha do tempo da branch `main` combinando duas partes: os cinco primeiros marcos (até o Merge PR #2) reproduzem o histórico real do repositório, com as branches `00davidsarago00-patch-1` e `docs` integradas via PR #1 e PR #2; os marcos seguintes (PR #3, PR #4, ajustes finais e a tag v1.0), marcados com nós vazados e linhas tracejadas, são uma projeção ilustrativa de como o mesmo fluxo de revisão por Pull Request se manteria até a conclusão da implementação e a entrega do projeto — não commits ou branches que já existem no repositório.

Esse é o nível de rastreabilidade que a equipe consegue demonstrar hoje: da mudança (PR) para o artefato afetado (arquivos alterados no merge) e para o ponto exato do histórico em que ela entrou na branch principal (o commit de merge). Não existe ainda uma matriz formal ligando cada requisito ou issue a um PR e a um caso de teste específico, porque o projeto não usa um sistema de issues de forma sistemática. Ampliar esse rastreamento, vinculando issues do GitHub a PRs e a casos de teste, é um passo natural de evolução do processo, mas o que registramos aqui é apenas o que o histórico atual já evidencia.

## *Build*, integração e entrega

Não há, nas fontes do repositório, confirmação de um pipeline de integração contínua configurado; não existe, por exemplo, workflow do GitHub Actions ou equivalente no projeto até o momento desta produção. O que existe de fato, como descrito nas seções anteriores, é a prática de submeter alterações via Pull Request e revisá-las antes do merge para a `main`, o que já funciona como uma barreira mínima de controle de qualidade antes da integração, mesmo sem automação.

Sem essa automação, o processo de build e execução do sistema é, hoje, manual: a API .NET seria compilada e executada localmente ou em ambiente de implantação a partir do código da branch principal, com as migrations do Entity Framework Core aplicadas ao banco PostgreSQL antes da subida da aplicação, enquanto o SPA seria compilado separadamente por seu próprio processo de build, no framework definido para o front-end, e servido de forma independente da API.

Como recomendação de boas práticas de Engenharia de Software para a evolução do projeto — e não como algo já implementado — sugerimos que a equipe adote futuramente um pipeline de integração contínua acionado a cada Pull Request, capaz de restaurar as dependências (NuGet e npm), compilar back-end e front-end, aplicar as migrations em um banco de teste e rodar a suíte de testes automatizados antes de permitir o merge. Isso transformaria em verificação automática o controle de qualidade que hoje depende só da revisão manual do PR, reduzindo o risco de uma alteração quebrar o build da `main` sem que ninguém perceba antes da entrega.
